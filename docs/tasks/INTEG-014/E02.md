# E02 — Reproduced builds and memory accounting

Completed 2026-09-14 UTC. No firmware source changes, deployment, reset or
emulator run. Supervised pause before E03's stock-reuse audit.

## Flash and SRAM

All figures are bytes. Flash capacity is 131,072; the MOS external SRAM
reservation is 16,384. Rows are ordered by flash occupancy, largest first.

| Composition | Flash occupied | Flash free | Static SRAM | Heap arena | Stack reserve |
|---|---:|---:|---:|---:|---:|
| Ordinary EMOS, rebuilt | 130,915 | **157** | 6,826 | 7,510 | 2,048 |
| Bench telemetry EMOS, reproduced | 130,071 | **1,001** | 6,964 | 7,372 | 2,048 |
| Official MOS 3.0.2 ZDS release | 108,490 | **22,582** | Not measured | Not measured | Not measured |
| Stock MOS 3.0.2, current AgonDev rebuild | 102,055 | **29,017** | 2,779 | 11,557 | 2,048 |

The ordinary profile comment's 153-byte figure is stale: both this rebuild and
the retained ordinary v0.1.15 binary occupy 130,915 bytes, leaving 157. The
profile itself was left untouched to preserve preexisting source work.

Heap arena is capacity before allocator metadata and live allocations. The
2,048-byte stack reservation is a linker/runtime convention, not a measured
worst-case stack high-water mark. No on-chip user SRAM is appropriated. No
fresh ZDS compile or ZDS RAM map was available for this comparison; its flash
row uses the verified official binary, not the AgonDev map.

Stock AgonDev is 6,435 bytes smaller than the ZDS release. Ordinary EMOS adds
28,860 bytes relative to stock built through the same current port, and 22,425
relative to the ZDS release. Compiler/translation/runtime differences do not
explain the EMOS increase as generic compiler bloat. This is a size comparison,
not a speed comparison or a claim that each addition is redundant.

Initialised data occupies both flash initialiser bytes and SRAM; count it once
in each budget. BSS and the writable jump table occupy no image bytes. The
149-byte descriptor/reset slot comprises a 79-byte hostfs descriptor and 70
bytes of linker fill. There are no additional inter-section flash gaps in
these images. Every ledger reconciles with binary length and linker sections;
all object SRAM contributions sum exactly to static SRAM.

All EMOS-named objects account for 26,837 of the 28,860 added bytes; changes
in shared objects account for the other 2,023. The linked restricted runtime
occupies **5,773 bytes in every composition**, with identical member size
contributions. EMOS has not added a second linked C runtime in these builds.
Equal runtime size does not prove equal calling frequency or execution cost.

The two standalone UART diagnostic objects total 4,948 bytes. The three named
parallel transport objects total 3,059. These are audit leads, not permission
to remove features or a promise that removing files recovers exactly those
bytes. `emos.o` itself is the largest code and state addition. ELF sizes identify
`emos_cmd` (3,580 code bytes), `emos_discover` (2,588) and `emos_invoke` (1,379)
as useful entry points for E03. Their purpose, stock alternatives and required
contracts have not yet been assessed in this step.

Bench replaces UARTFLOW and adds telemetry plus associated paths: net flash
reduction 844 bytes, static SRAM increase 138 bytes. That is a composition
tradeoff, not an optimisation of equivalent functionality.
