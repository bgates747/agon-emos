# E06 — Receive service and competing UART traffic

## Executive summary

**Reject the four-byte FIFO-trigger change as a throughput fix:** it saves only
**0.70%** receive time, below the frozen5% floor, despite reducing receive-service
pulses by about60%. Source returns to the original one-byte trigger. E05's
**33.41% transmit improvement** remains the retained candidate.

Ordinary mainboard service traffic adds about1% to a large P4 upload, so it does
not explain the major sender gap. Both receiver settings pass18native cases
each; the FIFO alternative also passes384exact transfer cases and three
independent wire captures. A heavier observer caused a separately retained
concurrent-receive failure; its timing cannot represent native behavior.
Per-byte parsing and packet effects while RTS stops the peer remain the stronger
receive candidates. E06's bounded study is complete with the observation limits
below. **The physical recovery checkpoint is still blocked:** the original ESP
images are verified, but EMOS admission and original-ROM readback have not
returned. The spoken hardware cue has therefore not run. E07 waits for review.

The same six independent E04/E05 captures used for the sender comparison were
decoded again; no second baseline acquisition was made. Each contains exactly
4,626 return bytes and correct packets. RTS service pulses are an observable
proxy for receiver service, not an independently observed CPU interrupt count.

Total RTS assertion includes intervals overlapping bytes on the wire. It is
therefore larger than the approximately69.334ms of E05 idle under Agon

work contributes the longer pulses; a precise per-routine cycle attribution
was not captured and is not inferred from pulse width alone.

The quiet observer smoke passes exact P4 return and forward checks, both vector
restorations and normal SD recovery. Its UART1 wrapper records1,540entries for
4,626bytes, about3.004bytes/IRQ: the counter delays entry sufficiently to change
FIFO coalescing. Compare instrumented loads only with the same instrumented
quiet case. Native timing remains the independent wire observation above.

## Diagnostic qualification correction

The first full observer run returned normally after failing its first UART0
service case: six queries, zero UART0 IRQs/bytes, exact P4 data, restored vectors
and recovery0. The initial AgonDev `-Oz` object compiled
`diag_uart0_put(*p++)` with an increment of IY before loading the argument from
IY. The query consequently omitted its leading byte. This is a defect in the
generated diagnostic helper, not evidence of concurrent UART loss.

An indexed C helper now loads the byte before the call and increments afterward;
its object was inspected before repeat deployment. The first source, object,
binary, bound ROM identity and failed CSV are preserved locally. No generic
compiler changes are made under this task. A reduced generic-toolchain
reproducer remains a separate follow-up, not a claim that all postincrements
are affected. The rejected run is excluded from performance comparisons.

## Four-byte receive-trigger candidate

`c0f5952` changes only the owned receiver's initial FCTL setting, from07h to47h;
the setup still enables/clears FIFOs before admitting its peer. It leaves the
receiver C/assembly, register saves, parser,16byte drain, RTS and error policy
unchanged. Character timeout shares the enabled receive interrupt and delivers
short packets; see the official reference in the procedure. No active-FIFO
register changes are made by the diagnostic app.

Canonical ordinary and bench builds/link checks pass and retain130898/130054
bytes. Compared with the E05 bench image, the machine-code delta is exactly
one byte at128E0h (07h→47h), plus timestamp digits in the identity string.
The real UART ownership/register-boundary, keyboard receiver and transmitter
ASan/UBSan tests pass. Actual FIFO timeout behavior still requires hardware.

The candidate bench is `agon-emos-v0.1.17-b2026-09-14-07-00-36Z`, SHA256
`9f29541b65179d497141736470fe082b3e13768e007ae6711d33a82d48a1de20`.
Ordinary is `agon-emos-v0.1.17-b2026-09-14-07-00-50Z`, SHA256
`cd6f18a6426f58edf53ec8a9863a058034007f3497c3a1fade4c78368a48bf58`.
Two earlier local rebuilds labelled `fifo4`/`fifo4-ordinary` ran after an edit
guard rejected an ambiguous match; they contain the old trigger and were never
deployed or treated as the alternative. Actual candidate inputs are preserved
under `fifo4b`/`fifo4b-ordinary` and checked by source and binary hashes.

The first independent candidate capture confirms that the trigger change is
effective:925service pulses for4,626bytes (5.001bytes/pulse), against roughly
2,307pulses (2.005bytes/pulse). Yet receive wire time is108.882ms, only about0.7%
below E05. Total RTS assertion is69.903ms, median pulse55.042microseconds,
95th percentile129.625microseconds. Fewer, longer service batches still spend
substantial time parsing/effecting the same bytes while the peer is stopped.
This first observation is preliminary; the fixed three-capture comparison
determines the verdict. No assumption that the hardware ignored FCTL is needed.

All18native quiet/service cases,336full transfer cases and36mixed cases pass
with this candidate, including normal recovery. The measured firmware is the
existing bench telemetry composition with no active telemetry producer. The
ordinary composition was built and link-checked; its physical performance is
not established by these bench measurements.

than the5.480ms improvement floor. Neither pure nor mixed throughput meets the

source; it is not a selected production change.

| Native wire service metric | Trigger1 | Trigger4 |
|---|---:|---:|
| Service pulses for4,626bytes | 2,306–2,307 | 924–925 |
| Mean bytes per service pulse | 2.005–2.006 | 5.001–5.006 |

| 95th-percentile pulse, microseconds | 97.750 | 129.625 |

The trigger **did** change batching. Fewer, longer service intervals have little
effect on elapsed transfer time. RTS assertion and byte occupancy overlap, so
their separate duration changes cannot be added as independent savings. The
experiment supports focusing on work done for every byte/packet while the peer
is stopped; it does not provide an exact cycle attribution for each C helper.

E03's linked structure explains the remaining candidates: EMOS's UART0 entry
uses ten save/restore pairs versus stock's four, but the UART1 receiver also
checks/drains/parses bytes while RTS is asserted and the stock-effect adapter
saves, copies and restores16payload bytes per eligible packet. Reducing entries
alone has now been tested and is insufficient. No blanket assembly rewrite,
shared-parser-state shortcut or required-service suppression follows from this.

E07 can review the retained E05 C sender, the remaining per-byte sender cost,
and a minimal receiver/stock-effect adaptation. A precise raw mainboard converse
or FIFO-occupancy histogram still needs a lower-impact observation method; the
failed heavy observer must not be reused as a native performance oracle. No
ordinary-build hardware, rendering, broad stress or production parity claim is
made by this bounded study.

## Physical recovery checkpoint — incomplete

The preserved original EMOS SD image was downloaded and compared byte-for-byte
before the `FLASH mos` command was submitted. The subsequent reset check did
not produce a fresh keyboard epoch; the old ready status was only cached and
was not accepted as recovery proof. No original-ROM readback was obtained.

The already-planned original mainboard and P4 image restorations then passed
independent flash verification. A fresh reset/admission check with those restored
peers still did not establish EMOS keyboard/SD service. P4 is reachable, neutral,
session0 and not admitted; SD is offline. This does not establish whether the
eZ80 reset circuit failed, boot stalled or the ROM write failed. Do not guess
which happened or submit another blind flash/reset.

Both ESP images are back to their original versions; the actual eZ80 ROM and
final CLI/SD roundtrip still need verification. Root startup was never edited.
Generated generic-builder outputs were restored and hash-checked. Existing
unrelated source/profile/telemetry work is preserved. The next required human
observation is one press of the Agon's own reset button and the resulting screen
state. Hardware voice playback cannot currently be invoked; the previously
authorised emulator fallback will request attention. E06's task checkbox remains
open for this recovery/notification gate, despite completed measurements.
