# E06 — Receive service and competing UART traffic

## Executive summary

The original IRQ handlers pass all18quiet/service cases. Ordinary mainboard
queries add about1% to a large P4 upload; they do not explain the major sender
gap. A heavier observer causes a concurrent receive failure, so its counts and
timings cannot stand in for native behavior. Independent wire captures show
roughly two bytes per service pulse and substantial time with RTS asserted.
A four-byte FIFO-trigger alternative is now being qualified under the
[frozen procedure](E06-procedure.md). E07 remains paused for Author review.

## Native receive service, without the application observer

The same six independent E04/E05 captures used for the sender comparison were
decoded again; no second baseline acquisition was made. Each contains exactly
4,626 return bytes and correct packets. RTS service pulses are an observable
proxy for receiver service, not an independently observed CPU interrupt count.

| Metric | E04 three runs | E05 three runs |
|---|---:|---:|
| Return wire span, median ms | 109.610 | 109.606 |
| RTS service pulses | 2,307 each | 2,306–2,307 |
| Bytes per service pulse | 2.005 | 2.005–2.006 |
| Total RTS asserted, ms | 72.606 | 72.604–72.606 |
| Median / 95th-percentile service pulse, microseconds | 23.125 / 97.750 | 23.125 / 97.750 |
| Maximum service pulse, microseconds | 167.417 | 167.375–167.417 |

Total RTS assertion includes intervals overlapping bytes on the wire. It is
therefore larger than the approximately69.334ms of E05 idle under Agon
backpressure. Do not add these overlapping measures. Packet completion/effect
work contributes the longer pulses; a precise per-routine cycle attribution
was not captured and is not inferred from pulse width alone.

The quiet observer smoke passes exact P4 return and forward checks, both vector
restorations and normal SD recovery. Its UART1 wrapper records1,540entries for
4,626bytes, about3.004bytes/IRQ: the counter delays entry sufficiently to change
FIFO coalescing. Compare instrumented loads only with the same instrumented
quiet case. Native timing remains the independent wire observation above.

## Diagnostic qualification correction

The first full observer run returned normally after failing its first UART0
service case: six queries, zero UART0 IRQs/bytes, exact P4 data, restored vectors
and recovery0. The initial AgonDev `-Oz` object compiled
`diag_uart0_put(*p++)` with an increment of IY before loading the argument from
IY. The query consequently omitted its leading byte. This is a defect in the
generated diagnostic helper, not evidence of concurrent UART loss.

An indexed C helper now loads the byte before the call and increments afterward;
its object was inspected before repeat deployment. The first source, object,
binary, bound ROM identity and failed CSV are preserved locally. No generic
compiler changes are made under this task. A reduced generic-toolchain
reproducer remains a separate follow-up, not a claim that all postincrements
are affected. The rejected run is excluded from performance comparisons.

## Corrected observer: concurrent reception fails

The corrected build `integ014-dual-uart-r01-b2026-09-14-06-43-45Z`, SHA256
`0ee15e82fb4ca73a5ac0728f0fc017472d1b904f2d8b9f60300e6e523cd09d51`,
passes its three quiet cases. Its first concurrent service/return case fails:
P4 progress ends at6clock units (50ms) and536UART1entries. Mainboard mode replies
continue correctly. The15second observation reaches8,990UART0entries; the bounded
8,192byte raw capture contains819complete correct mode replies plus a prefix.
Capture overflow is reported, rather than writing beyond application RAM.

The closed CSV reports terminal status15, four rows, one failed case, restored
vectors0 and failed ordinary recovery35. Sparse HTTP confirms SD offline and
keyboard admission lost. One explicit Pi reset restores neutral keyboard and SD;
the CSV/raw capture and unchanged root startup are read back. This is **not** a
successful concurrent-transfer qualification or a literal CPU hang: the app
recorded completion, but normal route/service recovery failed.

UART0's added copy work could defer UART1 service long enough to exhaust its
FIFO before software RTS is asserted. This is a hypothesis, not a measured LSR
overrun or a wiring diagnosis. The receiver alternative is held while the same
quiet/service workload is tested with both original IRQ handlers installed.
That follow-up intentionally has no IRQ counts or mainboard payload capture.

## Original IRQ owners: service comparison

`integ014-dual-uart-r01-b2026-09-14-06-55-52Z`, SHA256
`a650d372bdf7fe6e0f55cd0e798f49b2fa68e58fe0f2931afa309f35ca907370`,
runs without either observation handler. All18P4 exact-data cases and normal
recovery pass. Mainboard mode replies are deliberately suppressed by ExCom,
so this variant does **not** validate their payloads or count either UART's
interrupts. The zero count/raw fields mean unavailable in this variant.

Three observations per cell; worst elapsed case first. Both forward loads use
the same256-byte foreground chunks. Percent change is service/quiet minus one.

| P4 measurement | Quiet mainboard, ms | Mode queries at60Hz, ms | Elapsed change |
|---|---:|---:|---:|
| Forward65,535, endpoint median | 1,409.907 | 1,423.925 | +0.994% |
| Return256records, MOS completion median | 116.667 | 116.667 | Below clock resolution |
| Forward4,096, endpoint median | 89.901 | 90.917 | +1.130% |

MOS-clock resolution is16.667ms. The return's approximately0.6ms endpoint
value measures enqueue work, not receive completion, and is excluded here.
Query production and replies are both in scope; this is not an isolated ISR
cycle measurement. The failure disappears when observer work is removed in
these tested cases. That supports observer-induced timing sensitivity, without
proving a particular FIFO error bit or universal concurrent-UART robustness.

The larger raw-observed mainboard burst was not run after the simpler observed
service case failed. A converse exact mainboard timing comparison remains
unavailable under the current ExCom effect gate without extra observation or
a separately scoped diagnostic hook. Do not claim that missing comparison passed.

## Four-byte receive-trigger candidate

`c0f5952` changes only the owned receiver's initial FCTL setting, from07h to47h;
the setup still enables/clears FIFOs before admitting its peer. It leaves the
receiver C/assembly, register saves, parser,16byte drain, RTS and error policy
unchanged. Character timeout shares the enabled receive interrupt and delivers
short packets; see the official reference in the procedure. No active-FIFO
register changes are made by the diagnostic app.

Canonical ordinary and bench builds/link checks pass and retain130898/130054
bytes. Compared with the E05 bench image, the machine-code delta is exactly
one byte at128E0h (07h→47h), plus timestamp digits in the identity string.
The real UART ownership/register-boundary, keyboard receiver and transmitter
ASan/UBSan tests pass. Actual FIFO timeout behavior still requires hardware.

The candidate bench is `agon-emos-v0.1.17-b2026-09-14-07-00-36Z`, SHA256
`9f29541b65179d497141736470fe082b3e13768e007ae6711d33a82d48a1de20`.
Ordinary is `agon-emos-v0.1.17-b2026-09-14-07-00-50Z`, SHA256
`cd6f18a6426f58edf53ec8a9863a058034007f3497c3a1fade4c78368a48bf58`.
Two earlier local rebuilds labelled `fifo4`/`fifo4-ordinary` ran after an edit
guard rejected an ambiguous match; they contain the old trigger and were never
deployed or treated as the alternative. Actual candidate inputs are preserved
under `fifo4b`/`fifo4b-ordinary` and checked by source and binary hashes.
